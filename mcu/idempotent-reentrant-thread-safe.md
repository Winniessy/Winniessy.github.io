# 幂等、可重入与线程安全

在驱动、RTOS 和通信协议代码里，经常会同时遇到“幂等”“可重入”“线程安全”这几个词。它们都和“代码在复杂执行环境下能不能正常工作”有关，但关注的不是同一件事。

可以先这样记：

- **幂等**：重复执行，最终结果不再继续变化。
- **可重入**：函数执行到一半被打断后，再次进入也不会破坏状态。
- **线程安全**：多个线程同时访问共享数据，结果仍然正确。

## 1. 幂等

### 1.1 定义

同一个操作执行一次和执行多次，对系统最终状态的影响相同。数学上可以写成：

```text
f(f(x)) = f(x)
```

判断一个操作是否幂等，可以先问两个问题：

- 重复执行会不会产生累积效果？
- 第一次执行和后续执行完成后，系统最终状态是否一致？

### 1.2 例子

下面这些操作通常是幂等的：

- HTTP `GET`、`PUT`、`DELETE`（具体还要看接口实现）；
- 把用户名称设置为固定值：

  ```sql
  UPDATE users SET name = 'Tom' WHERE id = 1;
  ```

- 把状态设置为“已完成”；
- 写 1 清除 MCU 的中断标志：

  ```c
  EXTI->PR = EXTI_PR_PR0;
  ```

- 把原子变量设置为固定值：

  ```cpp
  std::atomic<int> x{0};
  x.store(1);
  ```

重复执行这些操作，最终都还是同一个状态。

下面这些操作通常不是幂等的：

- 重复提交 HTTP `POST`，可能创建多条订单；
- 重复扣减账户余额；

  ```sql
  UPDATE account SET balance = balance - 100 WHERE id = 1;
  ```

- `counter++`；
- `x.fetch_add(1)`；
- 向队列追加一条消息。

### 1.3 幂等不等于并发安全

幂等只描述“重复执行后的最终结果”，不保证并发执行时没有竞争。

例如：

```c
RCC->APB2ENR |= RCC_APB2ENR_USART1EN;
```

这条语句重复执行，最终都可以得到 USART1 时钟使能位为 1，因此从结果上看是幂等的。但它本质上是读-改-写：

```text
读取寄存器 → 修改本地值 → 写回寄存器
```

如果另一个线程或中断同时修改了同一个寄存器的其他位，就可能出现更新丢失。因此，幂等和线程安全是两个不同维度的问题。

## 2. 可重入

### 2.1 定义

如果一个函数在执行过程中被另一个执行流打断，之后又再次进入该函数，函数仍然能够正确运行，这个函数就具备可重入性。

这里的执行流不只包括线程，还可能包括：

- 中断服务程序；
- 多个 RTOS 任务；
- 递归调用；
- 信号处理函数或其他异步执行上下文。

### 2.2 常见条件

一个函数通常更容易做到可重入，常见做法包括：

- 只使用参数和局部变量；
- 不修改共享的全局变量或静态变量；
- 不返回静态缓冲区或全局缓冲区；
- 由调用者提供输出缓冲区；
- 不调用本身不可重入的函数；
- 不依赖可能被另一个执行流改变的隐藏状态。

可重入函数通常不需要锁，也不应该在中断上下文中执行会阻塞的操作。不过“无锁”不是严格的数学定义，关键还是看函数是否能在嵌套或异步再次进入时保持正确。

### 2.3 可重入例子

只使用参数和局部变量的函数通常是可重入的：

```c
int add(int a, int b)
{
    return a + b;
}
```

由调用者提供缓冲区的格式化函数也更容易做到可重入：

```c
void format_value(int value, char *buf, size_t size)
{
    snprintf(buf, size, "%d", value);
}
```

`strtok_r`、`rand_r` 这类接口把状态通过参数交给调用者管理，因此比使用内部静态状态的版本更适合并发或嵌套调用。

### 2.4 不可重入例子

使用共享全局变量的函数通常不可重入：

```c
int counter;

void inc(void)
{
    counter++;
}
```

使用静态缓冲区的函数也存在问题：

```c
char *to_string(int value)
{
    static char buf[16];
    sprintf(buf, "%d", value);
    return buf;
}
```

如果函数在第一次调用尚未完成时被再次调用，两次调用会使用同一块缓冲区，结果会互相覆盖。

`strtok`、很多实现中的 `malloc` 和 `printf` 都不能直接当作中断安全函数使用。具体情况要看 C 库实现，但在 MCU 项目里通常应该把它们视为不适合 ISR 的函数。

### 2.5 中断中的限制

中断服务程序可能打断任意任务，也可能再次打断普通代码。因此 ISR 中调用的函数必须满足更严格的条件：

- 不能依赖未保护的共享状态；
- 不能睡眠或阻塞等待；
- 不能等待互斥锁；
- 不能调用会长时间运行或分配不确定资源的函数；
- RTOS 中应使用专门的 `FromISR` API。

“可重入”并不自动等于“中断安全”。一个函数即使没有共享变量，如果内部会阻塞、访问不可在 ISR 中使用的硬件或调用不可重入的库函数，仍然不能放进中断里。

## 3. 线程安全

### 3.1 定义

多个线程或任务同时访问共享数据时，程序仍然能够保持正确，这种属性通常称为线程安全。

线程安全主要解决的是数据竞争和访问顺序问题。常见手段包括：

- 互斥锁；
- 原子操作；
- 读写锁；
- 线程局部存储；
- 消息队列；
- 设计成无共享状态。

### 3.2 互斥锁保护

```cpp
std::mutex mutex;
int counter = 0;

void inc()
{
    std::lock_guard<std::mutex> lock(mutex);
    ++counter;
}
```

多个线程调用 `inc()` 时，互斥锁保证同一时刻只有一个线程修改 `counter`。

### 3.3 原子操作

```cpp
std::atomic<int> counter{0};

void inc()
{
    counter.fetch_add(1, std::memory_order_relaxed);
}
```

当操作只需要保证计数更新本身的原子性时，原子变量可以避免使用互斥锁。内存序是否使用 `relaxed`，要根据其他数据的同步关系判断，不能因为计数器使用原子操作就忽略整体内存可见性问题。

### 3.4 非线程安全例子

```cpp
int counter = 0;

void inc()
{
    counter++;
}
```

`counter++` 不是一个不可分割的动作，而是读、加一、写回三个步骤。多个线程同时执行时，可能互相覆盖结果，产生数据竞争。

## 4. 三个概念的区别

| 概念 | 关注点 | 典型场景 | 典型问题 | 常用手段 | 中断中安全 |
| --- | --- | --- | --- | --- | --- |
| 幂等 | 重复执行 | 重试、重复消息 | 重复扣款、重复下单 | 幂等键、状态机、唯一约束 | 与中断无直接关系 |
| 可重入 | 并发或嵌套进入 | 中断、递归、多任务 | 静态或全局状态被破坏 | 无共享状态、调用者提供缓冲区 | 通常更接近 ISR 要求 |
| 线程安全 | 多线程访问共享数据 | 多任务共享资源 | 数据竞争、可见性问题 | 互斥锁、原子、读写锁、消息队列 | 不一定 |

最容易混淆的是后两者。线程安全通常允许使用互斥锁，但中断不能阻塞等待锁；因此“线程安全”的函数不一定能在中断里调用。

## 5. 三者可以独立组合

这三个概念是相互独立的，一个函数可以满足其中一个、两个，也可以三个都满足。

| 组合 | 例子 |
| --- | --- |
| 幂等、可重入、线程安全 | `std::atomic<int> x; x.store(1);`，前提是该原子操作在目标平台上可用且满足需求 |
| 幂等，但不可重入、未必线程安全 | `RCC->APB2ENR |= ...`，重复执行结果相同，但读改写可能和并发访问冲突 |
| 可重入，但不幂等 | `rand_r(&seed)` 会改变调用者传入的 `seed`，每次结果不同，但各执行流管理好自己的状态即可 |
| 线程安全，但不可重入 | 用 `std::mutex` 保护的 `counter++`，多线程安全，但中断里等待锁可能死锁 |
| 三者都不满足 | 未加保护的全局 `counter++` |

因此，看到一个函数时，不能只问“它安不安全”，而要继续问：

1. 重复调用会不会产生额外效果？
2. 被打断后重新进入会不会破坏状态？
3. 多个线程同时调用时，共享数据是否受到保护？

## 6. Cortex-M 和 RTOS 中的实践

### 6.1 中断服务程序

ISR 应该尽量短，只做必要的状态读取、标志清除和数据搬运。需要调用其他代码时，优先选择明确支持 ISR 的接口，避免：

- `malloc`、`free`；
- `printf`；
- `strtok`；
- 互斥锁和可能阻塞的函数；
- 执行时间不确定的复杂处理。

### 6.2 中断与任务共享数据

共享数据可以根据场景选择：

- 原子变量；
- 关中断临界区；
- RTOS 提供的临界区接口；
- 消息队列、信号量和任务通知；
- 专门的 `FromISR` API。

如果数据量较大，通常让 ISR 只记录事件或投递指针，再由任务完成主要处理。

### 6.3 通信协议重试

通信可能因为超时、丢包或设备复位而重试，所以接口设计时要考虑幂等性。例如：

- 使用请求序号或幂等键识别重复请求；
- 用明确的状态机记录操作是否已经完成；
- 对“设置状态”使用目标状态，而不是无条件累加；
- 对扣款、写 Flash 等有副作用的操作保存执行结果。

### 6.4 多任务共享资源

多个 RTOS 任务访问同一个外设或数据结构时，需要明确所有权和同步方式。常见选择是：

- 互斥锁保护短临界区；
- 消息队列把操作集中交给一个任务；
- 原子变量处理简单状态；
- 读写锁保护读多写少的数据。

不要只因为某个操作“重复执行没问题”，就认为它已经具备并发安全性。

### 6.5 Cortex-M0/M0+

在 Cortex-M0/M0+ 上，某些 `std::atomic` 操作可能不是 lock-free，具体要看编译器、数据宽度和目标架构。如果原子实现内部需要锁，就不适合直接放进中断中使用。需要时可以使用目标平台提供的原子指令、短临界区或关中断保护。

## 7. 总结

```text
幂等：重复执行，不产生额外的最终效果。
可重入：被打断后再次进入，状态仍然正确。
线程安全：多个线程同时访问，共享数据仍然正确。
```

嵌入式开发中，可以按场景来判断：

- 中断上下文优先关注可重入和不阻塞；
- 通信重试优先关注幂等；
- 多任务共享数据优先关注线程安全；
- 三者没有必然的包含关系，不能把其中一个当成另外两个的替代品。
